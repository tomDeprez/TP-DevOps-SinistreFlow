Mise en situation

Lundi, 9 h. Vous arrivez chez MutuAlp Assurances, mutuelle régionale de 45 000 sociétaires. Le lead dev, Thomas, est parti il y a un mois. Il a laissé une note, un dépôt Git, un dump de la base de production… et aucune documentation d'exploitation.

0métrique, alerte ou pipeline

👤 Les assurés

Déclarent leurs sinistres (accident, vol, dégât des eaux…) via un formulaire en ligne en 4 étapes.

🗂️ Les gestionnaires

Instruisent les dossiers dans le back-office : recherche, changement de statut, suivi de l'indemnisation.

🔧 Les partenaires

Le cabinet ExpertAuto récupère les dossiers à expertiser et dépose ses rapports via l'API. Leur connecteur tourne sur votre serveur… et vous n'avez pas le droit de le modifier.

La situation est critique. Le connecteur ExpertAuto est en échec : plus aucune expertise n'arrive, donc plus aucune indemnisation n'est versée. Le support a ouvert 22 tickets. Le CTO propose de « supprimer les vieilles versions de l'API pour simplifier ». La direction veut savoir avant vendredi si l'application peut être redéployée proprement sur un nouveau serveur, et surtout être prévenue la prochaine fois que ça casse.

02

Règles du jeu

✅ Obligatoire

  • Un dépôt GitHub par équipe (formateur invité en Admin).
  • main protégée : on passe uniquement par des Pull Requests relues par un coéquipier.
  • Une branche par ticket (fix/SF-104-reference-sequence).
  • Un commit par correction, avec le message exact donné dans le ticket. Le test qui prouve la correction va dans le même commit.
  • Un journal de bord d'équipe (docs/JOURNAL.md) : qui a fait quoi, chaque jour, ce qui a bloqué.

⛔ Interdit

  • Modifier partner-client/ : c'est le code d'une autre entreprise.
  • Supprimer ou désactiver un test pour « faire passer » la CI.
  • Modifier le dump db/dump/*.sql : c'est la vérité de la production.
  • git push --force sur main.
  • Committer un secret (mot de passe, clé, token).

Le format des commits

Le formateur vérifie automatiquement l'historique de chaque dépôt : un message différent d'un seul caractère n'est pas comptabilisé. Format Conventional Commits :

fix(SF-107): corriger le calcul de l'offset de pagination
 │     │        └─ description EXACTE du ticket
 │     └─ numéro du ticket
 └─ type : fix · feat · test · ci · docs

Pourquoi tant de rigueur ? En entreprise, l'historique Git est un outil d'exploitation : quand la production casse à 3 h du matin, on cherche quel commit a introduit le problème (git log --grep SF-, git bisect) et on le relie au ticket. Un commit = une intention = un retour arrière possible.

04

Le DevOps en un schéma

Le DevOps n'est ni un outil ni un poste : c'est une façon de travailler où ceux qui construisent le logiciel sont aussi responsables de son fonctionnement en production, et où tout ce qui peut être automatisé l'est, pour livrer souvent, sans peur.

Les 5 idées à retenir

🔁 Boucles de rétroaction courtes

Plus un bug est détecté tôt, moins il coûte. Un test unitaire répond en millisecondes, la CI en minutes, un client en colère en semaines.

⬅️ Shift-left

Ramener les contrôles le plus à gauche possible de la boucle : tests, sécurité, migrations, validés avant la production.

🤖 Automatiser la répétition

Ce qui dépend de « penser à… » finit par être oublié (SF-206). Ce qui est dans un script ou un pipeline est fait à chaque fois.

📏 Mesurer

Sans métriques, on ne sait pas si ça marche, ni depuis quand ça ne marche plus (SF-115). On supervise la technique et le métier.

🧩 Tout est code

Infrastructure, pipeline, configuration, tableaux de bord, alertes : versionnés dans Git, relus en PR, reproductibles.

🤝 You build it, you run it

L'équipe qui écrit le code est celle qui le déploie et qui est réveillée quand il casse. On écrit donc du code facile à exploiter.

Mission 0 · Prise en main

Jour 1 · matin

Objectif : avoir l'application qui tourne sur votre poste avec les données de production, voir le connecteur partenaire échouer, et savoir reproduire chaque ticket.

  1. Créer le dépôt de l'équipe. Un membre crée un dépôt GitHub privé à partir du code fourni, invite les coéquipiers et le formateur. Dans Settings → Branches, protégez main : Pull Request obligatoire, 1 approbation, pas de push direct (les status checks seront ajoutés en mission 5).
  2. Premier commit d'équipe. Créez docs/JOURNAL.md (composition de l'équipe, rôles, objectifs du jour) via une PR.
  3. Lancer la stack « comme Thomas ». 
    npm install
docker compose up -d db
bash db/restore.sh              # restaure le dump de production
npm run migrate                 # joue la migration 10
npm start                       # http://localhost:3000
    Sous Windows, utilisez Git Bash ou WSL pour les scripts .sh.
  4. Explorer. Formulaire (/), back-office (/backoffice.html), /health. Comptes de démonstration dans db/README.md. Explorez la base : docker compose exec db psql -U sinistreflow puis \dt, \d claims…
  5. Lancer le connecteur partenaire et constater l'échec. Copiez la sortie dans le journal : c'est votre « état zéro ». 
    export EXPERTAUTO_API_KEY=ea_live_7f3c9a1e5b2d4f60   # fournie par MutuAlp (voir .env)
python3 partner-client/expertauto_sync.py ; echo "code retour : $?"
  6. Lancer les tests existants (npm test). Ils passent… Est-ce une bonne nouvelle ?
  7. Cartographier. Dans docs/CARTOGRAPHIE.md : un schéma de qui appelle quoi, la liste des tables, et un tableau ticket → reproduit ? → commande de reproduction (curl, écran) → fichier suspect.

Reproduire avant de corriger. Un bug que vous ne savez pas reproduire, vous ne saurez pas prouver que vous l'avez corrigé. Gardez vos commandes curl : elles deviendront vos tests d'intégration.

curl -s -H "Content-Type: application/json" \
  -d '{"contractNumber":"MA-AUTO-001001","email":"camille.durand@example.test"}' \
  http://localhost:3000/api/public/contracts/verify

✅ Point de contrôle

  • Dépôt GitHub créé, main protégée, formateur invité
  • Application lancée localement avec le dump (425 dossiers visibles en base)
  • Sortie du connecteur ExpertAuto (en échec) consignée dans le journal
  • Cartographie et tableau de reproduction des tickets commencés

Mission 1 · Corriger les bugs

Jours 1 → 2

Les tickets sont rédigés par des utilisateurs : ils décrivent ce qu'ils voient, jamais la cause. Votre travail est de remonter du symptôme à la cause, de la prouver par un test, puis de la corriger, proprement, un ticket à la fois.

🔎 Outils pour localiser

  • Les logs de l'application (et leur absence !)
  • node --inspect src/index.js + Chrome DevTools, ou le débogueur VS Code
  • Les DevTools du navigateur, onglet Network
  • psql : \d claims, SELECT ... sur les données réelles
  • git log -p fichier, git blame : qui a changé quoi, et pourquoi
  • Les commentaires des migrations SQL

🧭 Conseils d'organisation

  • Répartissez les tickets dans un tableau GitHub Projects (À faire / En cours / En revue / Terminé).
  • Certains bugs en masquent d'autres : SF-114 rend tous les codes d'erreur faux, SF-102 cache SF-103…
  • Les tickets signalés 🔴 bloquent le partenaire : traitez-les en premier.
  • Les étoiles indiquent la difficulté estimée (★ à ★★★).

Les indices sont repliés. Ouvrez-les seulement après avoir vraiment cherché. Notez dans le journal les indices ouverts : cela fait partie de l'honnêteté professionnelle.

Mission 2 · Le dilemme des versions (SF-109)

Jour 2

Un champ ne remonte plus dans deux versions de l'API. Le CTO veut profiter de l'occasion pour supprimer les anciennes versions. Avant de toucher au code, vous devez comprendre, décider et documenter la décision : c'est ce que fait une équipe DevOps responsable de sa production.

1. Comprendre la cause : les données ont bougé, pas tout le code

2. Deux options sur la table

3. Notions à maîtriser

Changement cassant (breaking change)

Toute modification qui peut faire échouer un client existant sans qu'il ait rien changé : supprimer ou renommer un champ, changer son type ("125050" au lieu de 125050…) ou son unité, changer un code de statut, rendre un champ obligatoire, supprimer une route. Un changement cassant impose une nouvelle version.

Cycle de vie d'une version

Active → Dépréciée (on prévient : documentation, en-têtes HTTP Deprecation et Sunset, RFC 8594) → Retirée, quand on a mesuré qu'il n'y a plus de trafic. On ne retire jamais une version « parce qu'on pense » que personne ne l'utilise.

Tests de contrat

Pour chaque version : la liste exacte des champs, leurs types, leur format. Si un développeur modifie le schéma ou une requête, le test de contrat de la version concernée passe au rouge avant la production. C'est exactement ce qui a manqué en mars 2025.

Architecture Decision Record (ADR)

Un court document versionné avec le code : contexte, options, décision, conséquences. Dans deux ans, quelqu'un se demandera « pourquoi garde-t-on trois versions ? » : la réponse sera dans docs/adr/, pas dans la tête de quelqu'un qui est parti.

4. Ce qui est attendu

  1. Analyse. Retrouvez la cause exacte dans le code et prouvez-la en SQL (combien de dossiers concernés ? depuis quand ?).
  2. Décision. Rédigez docs/adr/0001-versioning-api.md avec le modèle ci-dessous (jalon du jour 2). Commit : docs(SF-603): ADR 0001 stratégie de versioning de l'API
  3. Correctif. Implémentez la décision. Commit : fix(SF-109): remonter l'immatriculation depuis vehicles dans les API v1 et v2
  4. Garde-fous. Tests d'intégration de contrat pour chacune des versions servies, et un test de cohérence : les versions servies décrivent le même dossier de la même façon (plaque, date, montants).
  5. Bonus. En-têtes de dépréciation sur la ou les versions à retirer à terme ; métrique d'usage par version et par partenaire (mission 7).
# docs/adr/0001-versioning-api.md
# ADR 0001 — Stratégie de versioning de l'API partenaires
- Statut : proposé | accepté | remplacé par …
- Date, décideurs, ticket

## Contexte          ← les faits : consommateurs, contraintes contractuelles, cause du bug
## Options étudiées  ← au moins 2, avec avantages / inconvénients / risques
## Décision          ← ce qu'on fait, en une phrase, puis le détail
## Conséquences      ← ce que ça coûte, ce que ça impose à l'équipe, le plan pour la suite

Rappel : le connecteur ExpertAuto ne sera pas modifié. Il doit passer au vert tel quel, dans la CI et sur votre VM. Une décision d'architecture se juge sur ses conséquences en production.

Mission 3 · Les 3 couches de tests

Jours 1 → 3

Un test répond à une question : « est-ce que ça marche encore ? ». Plus on monte dans la pyramide, plus la réponse est réaliste… et plus elle est lente, chère et fragile. Une bonne stratégie combine les trois couches.

Couche 1 · Tests unitaires

Ils testent une fonction isolée, sans base, sans réseau, sans serveur. Exécution en millisecondes : on les lance à chaque sauvegarde.

// tests/unit/indemnity.test.js
const { computeIndemnityCents } = require('../../src/domain/indemnity');

test('SF-106 : la franchise (en euros) est déduite en centimes', () => {
  expect(computeIndemnityCents(100000, 150)).toBe(85000);   // 1 000 € - 150 € = 850 €
});

test.each([['1250', 125000], ['19.99', 1999]])('%s -> %i centimes', (saisie, attendu) => { /* … */ });
  • ≥ 30 tests sur src/domain/, couverture des lignes ≥ 90 % (jest --coverage)
  • Les cas limites : J+5 / J+6, 29 février, montant nul, franchise > montant, saisie invalide…
  • Fuseau horaire fixé dans les tests qui manipulent des dates (process.env.TZ = 'Europe/Paris')
  • Le test historique faux (SF-105) corrigé

Couche 2 · Tests d'intégration

Ils démarrent l'application Express en mémoire (Supertest) et lui envoient de vraies requêtes HTTP, qui exécutent du vrai SQL sur une vraie base PostgreSQL restaurée depuis le dump. C'est la couche qui détecte les bugs « ça marche sur base vide ».

Mission 5 · Intégration continue avec GitHub Actions

Jour 3 · après-midi

L'intégration continue (CI), c'est un robot qui, à chaque Pull Request, refait exactement ce que vous devriez faire à la main avant de fusionner : installer, tester à tous les niveaux, construire l'image, et vérifier que le partenaire fonctionne. Si le robot dit non, on ne fusionne pas.

Exigences

  • Fichier .github/workflows/ci.yml déclenché sur pull_request et push sur main
  • Jobs unit, integration (conteneur de service postgres:16, restauration du dump, migrations), e2e (Playwright, rapport en artefact si échec)
  • Job partner : construit l'image, démarre la stack compose, exécute partner-client/expertauto_sync.py ; la clé est un secret GitHub
  • Job docker (sur main uniquement) : image poussée sur GitHub Container Registry, taguée avec le SHA du commit
  • Fuseau TZ: Europe/Paris dans les jobs de test, cache npm, versions d'actions figées (@v4)
  • Protection de main : les jobs unit, integration, e2e et partner sont des required status checks
  • Badge de statut du pipeline en haut du README.md
  • Bonus : job de vérification des messages de commit, scan de vulnérabilités, job deploy avec environnement protégé
# .github/workflows/ci.yml — point de départ
name: CI SinistreFlow
on:
  pull_request:
  push:
    branches: [main]
env:
  TZ: Europe/Paris
jobs:
  unit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npm run test:unit
  # integration: à vous (indice : jobs.<id>.services.postgres + psql -f db/dump/…)
  # e2e, partner, docker : à vous

Mission 6 · Déploiement sur une VM

Jour 4 · matin

La direction veut savoir si SinistreFlow peut être remonté sur un serveur neuf. Vous partez d'une VM Ubuntu vierge, vous la sécurisez, vous y déployez la stack, vous restaurez la base de production… et vous lancez le connecteur ExpertAuto depuis la VM. S'il est vert, la production est rétablie.

Étapes

  1. Obtenir la VM. Fournie par le formateur, ou créée par vos soins (cloud, VirtualBox, Multipass) : Ubuntu 24.04 LTS, 2 vCPU, 4 Go de RAM, 20 Go de disque.
  2. Sécuriser l'accès. Connexion par clé SSH uniquement, utilisateur dédié deploy (groupe docker), PermitRootLogin no, PasswordAuthentication no, fail2ban, mises à jour de sécurité automatiques.
  3. Pare-feu. ufw default deny incoming, puis n'ouvrir que 22, 80, 443. Vérifiez depuis votre poste avec nc -zv <ip> 5432 que la base est fermée.
  4. Installer Docker Engine et le plugin compose depuis le dépôt officiel Docker.
  5. Configurer. Code dans /opt/sinistreflow (clé de déploiement GitHub en lecture seule, ou image GHCR), .env de production avec des secrets neufs (openssl rand -base64 24), chmod 600 .env.
  6. Première mise en service. Démarrer la base, restaurer le dump, démarrer la stack (les migrations jouent toutes seules), vérifier /health.
  7. Reverse proxy nginx devant l'application, /metrics bloqué. Bonus : HTTPS avec certbot si vous disposez d'un nom de domaine.
  8. Le moment de vérité. Depuis la VM : 
    cd /opt/sinistreflow
SINISTREFLOW_URL=http://127.0.0.1:3000 EXPERTAUTO_API_KEY=… python3 partner-client/expertauto_sync.py
# SYNCHRONISATION CONFORME : 25/25 contrôles OK   ← capture d'écran dans le journal
  9. Automatiser. Scripts versionnés : deploy/provision-vm.sh (étapes 2 à 4), deploy/deploy.sh (pull de l'image, migrations, démarrage, attente de /health, connecteur, retour arrière automatique sur l'image précédente si échec), et docs/RUNBOOK.md (comment déployer, restaurer, réagir à chaque alerte).

Retour arrière et migrations. Revenir à l'image précédente ne « dé-migre » pas la base. Une migration doit donc rester compatible avec la version N-1 du code : on ajoute une colonne, on ne la renomme ni ne la supprime dans la même livraison (stratégie expand / contract). C'est d'ailleurs ce qu'avait fait la migration 8… à moitié.

Le connecteur consomme des données. Chaque exécution réussie fait passer un dossier en EXPERTISE_TERMINEE (10 dossiers auto disponibles dans le dump). Pour rejouer à volonté sur la VM : bash db/restore.sh puis docker compose run --rm migrate.

Mission 7 · Supervision

Jour 4 · après-midi

Le 14 septembre, la base est tombée et personne ne l'a su pendant 3 heures. Objectif : que l'équipe soit prévenue avant les utilisateurs, et qu'elle puisse comprendre ce qui se passe en un coup d'œil.

Que mesurer ?

Les 4 signaux d'or

Latence (combien de temps), trafic (combien de requêtes), erreurs (combien échouent), saturation (à quel point on est plein). Issus du livre Site Reliability Engineering de Google.

RED pour les services

Rate, Errors, Duration : pour chaque route de l'API. Un compteur de requêtes étiqueté par code HTTP et un histogramme de durées suffisent à tout calculer.

USE pour les ressources

Utilization, Saturation, Errors : CPU, mémoire, disque, connexions à la base. Fourni par les exporters, sans code.

TypeComportementExemple SinistreFlowRequête PromQL typique
Counterne fait que montersinistreflow_http_requests_total{route,status}sum by (status) (rate(…[5m]))
Gaugemonte et descendsinistreflow_db_pool_connections{state}max_over_time(…[10m])
Histogramrépartition par tranchessinistreflow_http_request_duration_secondshistogram_quantile(0.95, sum by (le) (rate(…_bucket[5m])))

Attention à la cardinalité. Une étiquette route="/api/v2/claims/SIN-2026-000450" crée une série par dossier : Prometheus explose. On étiquette avec le motif de la route (/api/v2/claims/:reference), jamais avec un identifiant.

Le test de panne (« game day »)

Une supervision qui n'a jamais sonné est une supervision dont on ne sait pas si elle marche. Sur la VM :

  1. Panne de base. docker compose stop db. Chronométrez : combien de temps avant que /health passe en 503, que l'alerte passe en firing, que la notification arrive ? Redémarrez, mesurez le temps de retour à la normale.
  2. Pluie d'erreurs. Une boucle de 200 appels avec une mauvaise clé API : quelle alerte, quel panneau le montre ?
  3. Mauvaise livraison. Déployez volontairement une image cassée (variable obligatoire manquante, par exemple) : deploy.sh doit revenir seul à la version précédente.
  4. Post-mortem. Pour chaque scénario, dans docs/JOURNAL.md : chronologie, captures Grafana / notification, temps de détection, temps de résolution, ce qu'il faudrait améliorer. Captures dans docs/preuves/.
